# ドキュメント管理運用ルール（README）

**作成日：2026年7月10日
適用範囲：多サイト展開プロジェクト全体（trip-matomeblog.com、oyako-shukatsu.com、および今後追加される全サイト）**

このファイルは、複数サイトを横断してドキュメントをどう管理するかを定めた運用ルールそのものです。**このルール自体が「共通ファイル」であり、全プロジェクトに複製配置します。**

\---

## 1\. 基本方針

情報ごとに「正本（Single Source of Truth）」を1つだけ定め、同じ結論を複数ファイルに書かない。これにより二重管理・ダブルスタンダードの発生を防ぐ。

## 2\. ファイル種別と配置ルール

|種別|役割|配置先|対象読者|
|-|-|-|-|
|**共通ファイル**|型・設計判断集・運用ルールなど、全サイトに共通する内容の正本|**全プロジェクトに複製アップロード**|全サイト共通|
|**サイト固有ファイル**|そのサイトだけの実装仕様・経緯・実務メモ|**そのプロジェクトのみ**|該当サイトのみ|

### 2.1 共通ファイル一覧（正本はこの3点のみ）

|ファイル名|内容|
|-|-|
|`README-document-management.md`|本ファイル。ドキュメント管理ルールそのもの|
|`shared-multi-site-playbook.md`|型・設計判断集（確定事項のみ）|
|`shared-site-construction-guide.md`|新サイト構築の汎用手順|

### 2.2 サイト固有ファイル一覧（サイトごとに作成）

| ファイル名パターン | 内容 |

|---|---|

| `\[サイト名]-spec.md` | 実装仕様書（関数名・判定フィールド等の技術詳細） |

| `\[サイト名]-analysis.md` | 経緯・振り返り（「なぜその型に至ったか」のみ。型の結論自体は書かず、shared-playbookへ誘導する） |

| `\[サイト名]-\[テーマ]-prep.md` | 個別の実務準備メモ（記事シリーズ準備等、都度作成） |

| `\[サイト名]-schedule-wbs.md` | 進捗管理・投稿スケジュール表（体験記事シリーズの投稿予定・実績を一覧管理） |---

## 3\. ネーミングルール

### 3.1 基本形式

* **全て半角小文字＋ハイフン区切り**（アンダースコアは使わない。将来ファイル名をown\_photo\_filesのようなカンマ区切りパラメータに渡す可能性がある運用と衝突しないため）
* 日本語・全角文字・スペースは使用しない

### 3.2 プレフィックスルール

* **共通ファイル**：`shared-` を先頭に付ける（例：`shared-multi-site-playbook.md`）
* **サイト固有ファイル**：サイト名（ドメインのメイン部分）を先頭に付ける（例：`trip-matomeblog-spec.md`、`oyako-shukatsu-spec.md`）
* **README系**：`README-` を先頭に付ける

### 3.3 命名パターン早見表

```
shared-\[内容].md              → 共通ファイル
\[サイト名]-spec.md            → 固有：技術仕様書
\[サイト名]-analysis.md        → 固有：経緯・分析
\[サイト名]-\[テーマ]-prep.md    → 固有：実務準備メモ
README-\[内容].md              → 運用ルール類
```

### 3.4 既存ファイルの名称移行（次回まとめて整理時に対応）

|現在のファイル名|新しいファイル名|
|-|-|
|`multi-site-playbook.md`|`shared-multi-site-playbook.md`|
|`site-construction-guide.md`|`shared-site-construction-guide.md`|
|`trip-matomeblog\_spec.md`|`trip-matomeblog-spec.md`（アンダースコア→ハイフン）|
|`trip-matomeblog-analysis.md`|変更なし（既にルール準拠）|
|`hakodate-series-prep.md`|`trip-matomeblog-hakodate-series-prep.md`（サイト名プレフィックス追加）|

## 4\. 二重管理を防ぐ鉄則

1. **「型」は確定してから複製する**：`shared-multi-site-playbook.md`内で「要検討」の印がついている項目は、まだ他サイトへ複製しない。確定した項目のみ複製対象。
2. **結論は1箇所にしか書かない**：`\[サイト名]-analysis.md`で型の話をしたくなったら、結論は書かず「詳細は`shared-multi-site-playbook.md`参照」と誘導する。
3. **spec.mdは実装詳細、playbookは一般論**：同じ判定ロジックの話でも、関数名レベルの詳細はspec.md、型としての一般論はplaybookに書き分ける。

## 5\. 共通ファイルの同期タイミング

* 毎回の細かい更新では複製し直さない。「要検討」段階のものは発生元サイトだけで育てる。
* 複製し直すのは**共通ファイルのバージョンが上がった節目のみ**（`shared-multi-site-playbook.md`にバージョン履歴を追加すること）。
* 各サイトのプロジェクトには、参照している共通ファイルのバージョンをメモしておくと、複製漏れを検知しやすい（例：spec.mdの末尾に「参照中：shared-multi-site-playbook.md v1.0」等）。

## 6\. 新サイト追加時の手順

1. 新規プロジェクトを作成
2. 共通ファイル3点（`README-document-management.md`、`shared-multi-site-playbook.md`、`shared-site-construction-guide.md`）の最新版を複製アップロード
3. そのサイト専用の `\[サイト名]-spec.md`・`\[サイト名]-analysis.md` をゼロから作成
4. 運用で得た知見のうち、確定した型のみ `shared-multi-site-playbook.md` に還元し、次回の同期タイミングで他サイトにも反映する
